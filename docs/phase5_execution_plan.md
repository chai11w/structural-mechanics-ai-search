## 2. 术语与权威

- **逻辑操作**：用户的一次明确意图，例如“查这张图”“用这个框重新裁剪”。同一操作可经过多个 HTTP 请求，但只能归入同一操作记录。
- **请求**：一次传输。`request_id/trace_id` 用于定位请求，不能充当操作去重证明。JSON/stream 不能各建一套逻辑操作身份。
- **任务身份**：会话执行代次 + workflow ID（standalone A2 可无父）+ child ID；A3 子题还须绑定父版本、unit ID 和裁图/输入版本。重置后禁止复用旧代次。
- **状态版本**：对影响操作允许性、目标、输入、结果的修改作单调条件写。现有父子 `task_revision` 和 `candidate_generation` 原义保留，不能偷偷改为通用状态版本。
- **执行尝试**：一次获准的实际执行，属于明确操作；用户显式重试产生新的尝试与可追溯关系，不能仅更换 trace/run ID 掩盖重跑。
- **调用**：一次模型或工具副作用；外部模型的有限 schema 纠错也要逐次归属，不能压成“只调用一次”。
- **权威分层**：Task State 表示业务当前态；操作/尝试收据证明执行；费用账本记录已确认费用；Trace/Checkpoint 是诊断证据。不得因为 Checkpoint 存在就授权恢复执行。

## 3. 操作身份和重发规则

1. 所有可变/可能计费入口在开始业务副作用前登记。上传读取和鉴权校验可先发生，但不能先执行模型/覆盖任务，再补收据。
2. 键作用域至少包括经服务端验证的身份、会话执行代次和客户端操作键。目标类型、任务/父子身份、输入摘要写入该记录。每次查重仍重新鉴权，不能凭键读到别人的结果。
3. 同一次网络重发保持原键、目标与输入。用户主动新上传、换裁剪、新章节或明确重新识别使用新操作，关联旧操作/尝试。相同图片内容不是自动合并不同意图的理由。
4. 摘要覆盖操作类型、图片内容摘要、bounds、章节/上下文、目标 unit、候选 generation/rank 等真正影响该操作的字段。unit 集合是否有序按接口语义明确，不可一律排序抹掉“先查哪题”。不包含 trace ID、临时媒体 URL 等传输字段。
5. 同键不同输入/目标必须冲突拒绝；缺失或非法键的外部可变请求不能静默退回不受保护执行。旧调用方可经明确适配器接入，但生成新键只表示新操作，不能宣称旧客户端重发已去重。
6. 查到原操作后再按其状态处理重复请求；不能只因任务版本已前进而丢掉可核对的原收据。历史结果读取与“再次允许执行旧动作”分开。
7. 已完成结果仅在身份仍有权、引用有效、输入/生产版本相符时复用。同操作缺失结果应返回已完成但结果不可用的事实，不自动重做模型或换题库版本；对新操作复用阶段产物还须验证输入、工具/模型/Prompt 版本和数据版本。
8. 过期操作键不能在清理收据后重新当新任务执行。5.2 必须确定服务端可信有效期、过期拒绝和去重墓碑保留策略；不以浏览器时间或 Checkpoint TTL 为唯一依据。

## 4. 运行、失败与恢复规则

设计状态可用 `REGISTERED / RUNNING / SUCCEEDED / FAILED / UNKNOWN / CANCELLED` 表达；公共字段名称留给后续契约，不能直接增加现有五态协议外的新状态。

| 已知事实 | 重发/恢复应做什么 | 禁止事项 |
| --- | --- | --- |
| 已登记，确定尚未开始副作用 | 原操作按当前权限和准入条件执行或继续等待 | 重新建一个独立操作绕开争用 |
| 正在执行 | 返回已有操作的可观察状态；持续执行由当前执行者负责 | 重发启动第二个执行者 |
| 已成功提交 | 返回原操作结论或重新交付有效结果 | 因响应丢失重新调用模型 |
| 明确失败，确认没有未知副作用 | 根据该阶段规则允许显式重试；记录新尝试及原因 | 把原失败记录覆盖成“从没执行” |
| 已发外部请求，但没有可信结果；或提交是否成功不明 | 标为未知/待对账，读取权威记录或供应商可用的请求结果；无证据时保持不确定 | 租约到期、断线、超时或查不到 Trace 就自动重放 |
| 业务成功但费用落账未确认 | 保留业务成功事实及单独待记账状态，以相同调用身份核对/补账 | 再执行业务来补费用；把未知费用当成零 |
| 已取消/结束/重置 | 拒绝旧副作用提交；保留可核对的终态/旧代次墓碑 | 旧模型返回把任务重新激活 |
| 部分 unit 成功、其余失败 | 保留各 unit 确认结果，只按规则处理失败/未知项 | 整批重放已成功项 |

执行争用需要数据库原子登记/条件更新；进程内锁可保留以减少竞争。执行者 token 必须参与结果提交校验；租约过期只说明持有者失联，不能证明外部请求未执行。不能把本地互斥宣传为供应商“恰好一次”。

父子关系更新和结果提交必须有明确事务或可对账交接协议。不得对现有父库、子库、费用库做“分别写一下便算成功”的假设。恢复必须逐条处理已有尝试，阶段 5 不新增后台任务调度生命周期。

控制操作也在相同授权/版本/收据机制内：停止当前子题、结束整页、重置会话语义分开；在途模型不能承诺立即取消。旧执行即使返回，也只有其原归属下的历史证据资格，没有覆盖新状态的资格。

## 5. 副作用与计费边界

- **模型调用**：先持久记录尝试与调用身份，再标记发送和记录可确认结果；发送与供应商接收之间不能本地原子化，故必须保留 UNKNOWN 分支。逐个审计 client/SDK 自动重试和有限 parser 纠错，区分已知结果重做与传输未知重放。
- **搜索/复筛**：只读题库并不代表整个阶段无副作用，复筛可能调用模型。复用产物需匹配输入和生产版本；保持章节边界、原脚本识别逻辑与候选排序。
- **裁图/答案文件**：在隔离目录写不可变产物，验证完成后发布引用；数据库提交失败可能留下孤儿文件，清理不得删除仍被有效操作引用的结果。准备文件成功与浏览器收到文件是两个事实。
- **费用**：复用现有账本主键保护，新增稳定 operation/attempt/call 关联及可核对的写入交接。相同调用费用重复写应核对内容一致并复用；同 ID 不同费用内容必须报冲突，禁止覆盖。新的一次授权模型调用可以产生新费用。
- **跨库中断**：业务结果提交后、费用提交前的中断必须可诊断并补记；费用已提交而 ACK 丢失时先按同 ID 核对；不得创建新 run ID 盲写。账本不可用期间遵守既有预算策略，不把待计费用从额度计算中无声丢掉。
- **保留/容量**：5.2 确定执行收据、去重墓碑、结果引用的期限与硬容量门；活跃或待对账记录不得被普通过期清理误删。清理、隐私范围和重置语义要兼容。不得记录密钥、完整 Prompt/模型原文；复用结果不要求复制诊断层禁止保存的内容。

## 7. 实现选择与下一步

推荐增量扩展现有 SQLite 体系，保留检索工具和 V1 展示契约；先把身份/版本和执行记录的权威、事务边界定清，再接持久执行。更简单的“只补内存 fence/按钮禁用”可以减少部分重复请求，但不能满足重启与跨库故障保证；更快的单入口试点可作为 5.3 开发切片，不能代替全部入口验收。当前证据不支持为此直接引入新调度框架。

5.2 已落实的设计决定（细节及验证见上述两个实现契约）：

1. 新执行权威表与现有父/子 session 库如何共存；选定单事务域或明确交接协议、失败状态和读写顺序，避免双权威。
2. 通用版本、会话代次、父子外键和历史尝试字段；旧状态导入只标记 legacy 当前态，不伪造过去执行收据。
3. 操作键有效期、服务器可信时钟、去重墓碑/活跃/待对账记录保留及容量数字。
4. 旧客户端和直接 runtime 调用的适配/拒绝策略，以及新 public 字段/错误码怎样兼容原五态协议。
5. 数据变更的隔离迁移、回退与相关 launcher 参数；不得直接在 8790/8795 或旧飞书运行库上试迁移。

这些数据门已在隔离分支落实，后续进入 5.4 失败、费用与父子收尾；生产迁移仍须经过 5.5 验证及单独的发布安排。
