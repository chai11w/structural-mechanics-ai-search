## 改动

- 分开处理等待响应、读取正文、协议校验。JSON 形状或语法错误归 `RESPONSE_INVALID`，不伪装成网络断开；真正 fetch/正文传输中断保留有界恢复。
- 每次绑定生成独立随机 `X-Request-ID`。失败只记录版本、请求编号、阶段、错误类别、整数耗时和 HTTP 状态；不记录原始异常、URL、图片、题目、Cookie、邀请码或操作参数。
- 独立 sessionStorage 键 `tiku-agent-bind-diagnostics-v1` 最多保留 16 条记录和一条待回传记录。读取损坏、禁止存储、容量不足或随机编号不可用不阻断业务。
- 下一次已有的绑定请求通过 `X-Tiku-Bind-Diagnostic` 带回上一条失败；不增加请求。成功绑定后清除待回传标记，保留本标签页的有界历史。完全离线且尚无后续请求时，后台仍收不到该证据。
- 服务端只在通过认证的精确绑定 POST 上解析最多 512 ASCII 字节、精确字段和枚举；无效诊断忽略。现有服务日志以 `BIND_TRANSPORT_DIAGNOSTIC` 前缀保存单行 JSON，包含当前权威 request_id 和明确标记为客户端自报的 `client_bind_*` 字段。前次请求编号不覆盖本次身份；公共响应不增加内部诊断，日志故障不阻断业务。
- 共享 Trace 不新增属性或存储结构，避免旧版本严格读取器拒绝新记录；用服务日志中的随机请求编号对应现有 Trace 即可核对服务端处理。
- Trace 为 `/api/jobs/session` 保留独立端点名，任务编号等动态路径继续归一化，便于对应客户端记录。
- 绑定成功但执行上下文变化时，仍返回 STALE，并明确业务尚未提交，避免误判成等待原任务。

绑定仍最多两次，每次 15 秒，间隔 500 毫秒。业务 POST 不自动重发；刷新、观察、重连不会调用历史 UNKNOWN 模型。CLI、飞书、模型恢复策略、认证、费用与会话 TTL 不变。

## 如何判断下一次真实失败

从服务日志读取 `BIND_TRANSPORT_DIAGNOSTIC` 白名单 JSON，用 `client_bind_request_id` 查询前一次请求的服务端 Trace；`request_id` 对应带回诊断的本次绑定：

- 前一次有快速成功终态而客户端报正文中断或超时：继续排查响应交付与浏览器侧；服务端成功不等于浏览器收到。
- 前一次服务端也慢：依据权威请求耗时排查服务器排队、鉴权或绑定处理。
- 找不到前一次请求：入口前链路或日志覆盖仍需核对，不能单凭缺失下结论。
- `phase=protocol` 且 `code=RESPONSE_INVALID`：检查响应格式，不再归因于模型或泛称用户网络问题。

客户端记录是诊断线索，不是任务执行、费用、权限或重发授权的依据。真实连续换题的稳定性仍须上线后按该证据验收。
