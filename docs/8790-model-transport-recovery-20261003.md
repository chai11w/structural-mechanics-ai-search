# 8790 必要视觉步骤的单次传输恢复

2026-10-03，用户授权修复主线间歇模型调用失败。目标是让必要视觉步骤在已观察到瞬时传输失败后，本轮可以追加一次独立调用，同时保留首次调用的 UNKNOWN、费用及任务证据。这是有限恢复能力，不代表已经证明网络断开的根因。

## 已核实的故障

以下时间均为北京时间。调查只读生产与演示运行记录，没有为调查重新调用模型。

| 时间与步骤 | 主线记录 | 演示对照 |
| --- | --- | --- |
| 11:52:58 开始的整页任务；11:53:35–11:53:55 裁图比较 | `g1-u3` 的 `qwen_a3_crop_compare` 在 19.631 秒后发生 `URLError → SSLEOFError(errno=8)`；同批另两路在 2.935、2.759 秒成功。任务转手动裁剪并完成。 | 11:54 同一原图的三路比较均一次成功，分别耗时 2.381、2.628、2.655 秒。 |
| 12:01:36–12:01:56 的单元图像分类 | `g1-u1` 的 `qwen_image_classification` 在 19.407 秒后发生相同 SSL EOF，操作保留 UNKNOWN。 | 12:03 同一单元分类在 2.497 秒后一次成功。两路实际裁图的字节数和 SHA-256 相同。 |

首次上传原图的大小为 179495 字节，两路 SHA-256 相同；第二组分类对照使用的裁图为 25044 字节，SHA-256 也相同。演示的调用计数已核对实现：`request_json_with_retry` 的实际尝试次数进入费用记录，上述成功均为 `attempt_count=1`，不能用隐藏重试解释这两组差异。

主线异常栈位于 `http.client._send_output → send → ssl.sendall → ssl.send`。已核对生产 Python 的 `_send_output` 对应请求正文 chunk 的发送位置，因此这两次失败发生在 HTTPS 请求正文上传阶段，不能称为模型推理超时或并发门禁等待。10 月 2 日 23:52 的 GLM 自动裁图也留下相同上传阶段 SSL EOF，单纯替换 Qwen 不能保证消除此类故障。

演示也存在失败。10 月 3 日 00:01 的 GLM 自动裁图记录 `URLError`，耗时 19.249 秒；12:04 的 Qwen 长度决胜记录 `TimeoutError`，耗时 12.064 秒。后者仍于 12:04:06 交付四个候选。主线同样已有 `length_existing_order` 等明确业务降级，不是所有模型失败都会终止任务。

失败率比较必须包含 UNKNOWN 记录：主线使用 `execution_effects.record`，不能只查成功费用表。故障样本显示的是间歇传输失败；现有证据不足以归因于模型能力、特定网络组件、运行账号或代理。

## 恢复语义

- 8790 启动入口显式启用此能力，通用执行策略及应用构造函数默认关闭。只针对必要视觉步骤中首次已观察到、符合白名单的瞬时传输失败；每个受保护步骤最多追加一次调用。
- 追加调用是新的独立调用，使用新的 `call_id`、`run_id` 和成本收据，独立经过费用准入与记账流程。它不覆盖首次调用，也不把首次 UNKNOWN 改成成功或零费用。
- 仅在当前活跃执行轮次内自动恢复。后台观察、轮询、重连、进程重启及历史任务恢复不得据此重放旧 UNKNOWN，也不得生成第三次自动调用。
- 第二次仍失败时，沿该步骤已有业务降级或 UNKNOWN 路径结束；有手动裁剪、已有候选顺序等明确降级时继续按原语义交付，必要识别缺失时不得编造荷载或识别结果。
- 费用准入、费用落账、收据保存、业务解析及权限错误不触发传输恢复；不能通过重复请求绕过这些错误。
- CLI、旧飞书及 8888 演示入口不启用该能力。8790 可使用 `--disable-model-transport-recovery` 关闭追加调用。

首次调用可能已经部分发送，费用或远端效果仍未确认；允许本轮独立恢复不意味着首次调用不存在，也不意味着两次调用只计一次。原始收据及费用不确定性必须持续保留。

恢复关系与首次 UNKNOWN 在同一事务中登记，避免并发题目看到无恢复记录的中间状态。第二次失败尚未登记业务降级时，也不会阻断其他题目的独立调用；最终交付仍逐条检查恢复成功或明确业务降级，不能凭恢复意向伪造成功。首次失败所在费用批次维持原待核语义，补调用的已知费用使用独立批次落账。
