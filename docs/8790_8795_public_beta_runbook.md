# 8790 / 8795 小规模公网内测清单

本清单只服务于 2～3 人、约 24～48 小时的邀请制验证。8795 仍是过渡管理后台，不在本轮扩建 Trace 页面或长期后台架构。

## 1. 发布边界

- 测试者只获得 8790 地址和各自的邀请码，不获得 8795 地址、管理员密码或后台截图中的敏感信息。
- 8790、8795 origin 都只监听 `127.0.0.1`，公网只经过各自独立的 Cloudflare Tunnel。
- 不复用 8788 飞书 Tunnel、端口、配置、状态目录或 Cookie。
- 不做路由器端口映射，不把本机 origin 直接暴露到公网。
- 每名测试者使用独立邀请码、独立估算费用软额度和 7 天有效期，不共用邀请码。

## 2. 本机发布前

1. 先完成聚焦测试和全仓回归，只暂存本轮文件并提交、推送；记录发布提交号，并确认本轮代码没有未提交或未跟踪文件。Git Bundle 不能保存未提交改动，所以不允许把脏工作区当作代码回退点。
2. 在仓库外创建本次专用备份目录，先关闭 ACL 继承，只允许当前运行账号、SYSTEM 和管理员访问，再写入任何副本。创建并验证包含全部 refs 的 Git Bundle，记录其 SHA-256。
3. 对下列存在的数据库分别使用 SQLite 在线备份 API 建立一致副本并执行 `integrity_check`，不要只复制 WAL 模式主文件：8795 `control.sqlite3`；8790 根 `model_costs.sqlite3`、`a3_sessions.sqlite3`、`feedback.sqlite3`、`trace_events.sqlite3`、`responses.sqlite3`；当前子 A2 的 `a2/session.db`；以及 8795 仍会读取的 `a2/model_costs.sqlite3` 历史库。旧根 `session.db` 不属于当前 A3→A2 装配。
4. 将 `control.sqlite3` 副本与当前 `invite_code_encryption.key` 成对保存；分别计算源密钥和副本密钥 SHA-256，必须完全一致。备份清单只写哈希、PID、时间和布尔检查结果，不写邀请码、密码、完整命令行或数据库内容。
5. 确认 live 控制库与加密密钥没有向普通本地用户开放修改权限；若存在宽泛 `Authenticated Users: Modify`，在保留所有者、SYSTEM 和管理员访问的前提下收紧后复核。
6. 确认 8790 生产参数为 1 个活动任务、2 个排队任务、55 秒排队超时；确认 8790、8795 的 `/health` 都只从本机返回成功。`/health` 不能证明队列为空，切换前还须暂停测试者 Access/邀请码并人工确认没有在途请求。
7. 用 PID、可执行文件、完整启动参数、监听地址和启动时间共同核对 8790/8795；只看端口或只看进程名不够。记录 8788、8793、8794、8891、8896、8897 的监听 PID，作为切换前受保护端口快照。
8. 确认仓库、服务日志和交付文件中没有 Tunnel token、管理员密码、邀请码明文、API key 或 Access Cookie。

## 3. 精确冷启动新版

本轮 8790 已经使用 8795 控制库，不使用 `switch_tiku_agent_8790_control.ps1` 做代码发布。该脚本用于早期控制库迁移，不代替本清单的受限 ACL、完整进程身份和冷启动验证。

1. 先读取两个看门狗 PID 文件，并用进程命令行确认其确为对应脚本。若旧看门狗仍存活，先精确停止旧看门狗；不得直接启动新版形成双重监管，也不得按端口批量杀进程。PID 文件缺失或失效时，必须先通过进程命令行审计确认没有遗漏的旧看门狗。
2. 精确核对当前 8795 服务 PID 后只停止该进程，确认 8795 端口释放；隐藏启动新版 8795 看门狗，显式传入项目 Python、8795 管理运行目录和 8790 数据源目录。
3. 等待 8795 健康后，再核对新看门狗 PID、服务 PID、启动时间、完整命令行和 `127.0.0.1:8795` 唯一监听者。至少经过一个 20 秒巡检周期，确认看门狗仍存活且 PID 文件没有漂移。
4. 用同样方法精确停止当前 8790 服务，只以 1/2/55 和控制库参数隐藏启动新版 8790 看门狗。确认 `127.0.0.1:8790` 唯一监听者、健康响应、Trace writer 无失败，并经过至少一个 20 秒巡检周期。
5. 对比切换前后的 8788、8793、8794、8891、8896、8897 监听 PID，必须完全不变。把新旧 PID、启动时间、发布提交号、健康布尔值、数据库检查和受保护端口对照写入脱敏 postflight 清单。
6. 任一步身份核对失败立即停在现场；不得按端口清理未知进程，也不得自动恢复控制库。先停用测试入口，再依据已验证的代码锚点和数据库/密钥成对备份制定回退。

## 4. Cloudflare 控制台

这部分是 Cloudflare 账户状态，仓库脚本不会代替执行。不要把 Tunnel 凭据或策略导出文件提交到仓库。

1. 分别核对 8790 和 8795 的 Public Hostname 指向各自的 `http://127.0.0.1:<port>`，不要交叉指向。
2. 给 8795 创建 Self-hosted Access Application，只允许管理员邮箱。
3. 给 8790 创建独立的 Self-hosted Access Application，只允许本轮测试者邮箱；邀请码作为第二道门禁。
4. 不给公网 `/health` 设置绕过策略；本地看门狗不经过 Access，不受影响。
5. 创建两条窄范围 Rate Limiting 规则，按当前套餐选择最接近的可用时间窗：
   - `POST /api/admin/login`：约 10 次/分钟/IP，命中后阻断约 10 分钟。
   - `POST /api/invite/login`：约 30 次/分钟/IP，命中后阻断约 10 分钟。
6. 测试期先不开宽泛的 Bot Fight Mode 或全站挑战，避免图片上传被误伤；只启用 Access 和登录路径规则。

应用层还有兜底限速：8795 为同一客户端 10 分钟内 5 次失败，8790 为 10 分钟内 10 次失败。它们使用有容量上限的进程内状态；成功登录会清除已经完成的失败记录，但不会清掉同一客户端仍在进行的其他登录尝试，服务重启会清空全部进程内状态。该兜底不能替代 Cloudflare 边缘规则。

## 5. 专用邀请码闭环

使用不交付给测试者的专用邀请码完成一次真实闭环：

1. 新设备或无痕窗口通过 8790 Access，再进入邀请码页。
2. 登录并刷新页面，确认登录仍有效。
3. 提交一张 A2 普通单题。
4. 提交一张 A3 多题页，完成选题和其中一题检索。
5. 发送一次文字追问。
6. 对一条回复点赞、对另一条回复点踩。
7. 在 8795 核对已记录页数、题数、模型估算费用、反馈提交时间、反馈范围和候选数。
8. 反馈详情应把新版回复标为“服务端回复已核对”；关联费用、记录开始/结束和模型记录明确标为估算关联；页面侧候选等待明确说明来自页面时间线。
9. 停用专用邀请码，确认该浏览器下一次访问 8790 时立即要求重新登录。

不要用单条反馈的关联费用核对供应商账单。今日总费用是 Token 与价目表的模型估算；单条反馈费用还会受重试、同页多题和记录缺失影响。

## 6. 发放与观察

- 先只发给 2～3 人，建议错峰开始；第 4 个同时到达的任务会直接收到繁忙提示，排队超过 55 秒会提示重试。
- 每人使用独立邀请码，默认 7 天有效；额度只设为本轮可接受的模型估算费用。
- 观察 24～48 小时，重点记录：成功闭环率、排队超时、A3 裁图失败、候选相关性、图片交付失败、点踩原因和估算费用增长。
- 不因为少量测试顺利就立即增加功能。先判断问题来自题库覆盖、检索质量、图片路线、交互说明还是后台可观测性。

## 7. 停止与回退

- 发现费用异常增长、连续 5xx、反馈内容错绑或控制库异常时，先停用测试邀请码，再撤销 8790 Access 测试者策略。
- 只停止或重启 8790、8795 的精确目标进程，不触碰 8788、8793、8794、8891、8896、8897。
- 代码或启动失败时只回退到上一已验证代码与启动配置，不回滚正常的邀请码状态和审计记录。只在确认控制库损坏或迁移失败时，才用验证过的在线备份副本与对应加密密钥成对恢复。
- 测试结束后，反馈案例保留清理由独立 retention 流程执行，继续遵守 `plan → confirm → backup → apply`，不直接删除运行目录。
