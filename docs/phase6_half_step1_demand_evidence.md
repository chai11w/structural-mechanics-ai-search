# 阶段 6½ 第一步：暂停与停止需求证据

核对时间：2026-09-23 12:35（北京时间）。本步只读核对 8790 运行状态、执行库聚合、共享反馈库、当前网页资源和相关代码；没有读取题图、用户正文、邀请码或密钥，没有提交业务请求或调用收费模型。

## 结论

用户明确描述的首要痛点是：题目提交后必须等待跑完，页面上没有可用的暂停或停止操作。这是直接需求证据。当前 8790 网页确实隐藏了执行控制面板；已有服务端的“停止当前题/结束本页”控制以已保存的题目状态为目标，也不能据此承诺从接收任务起随时停止。关闭或刷新网页后原任务继续、回来查看结果属于已经实现的另一种能力。

用户给出两种希望支持的回头动作：误传图片后中止原任务并上传新图；误点暂停后继续原任务。用户进一步选择：新图被接收后可以放弃旧题，不要求把两个题目都留作可继续任务。另一个“发现章节识别错误后暂停，说一句换个章节搜”的例子，用户明确说明尚属设想。这些是具体的产品需求场景，不等于已发生的事故次数。前两者分别涉及放弃旧任务与恢复原任务；改章节涉及修改检索条件，不能当作原输入的简单恢复。

因此第 6½ 阶段的下一步应先定义“停止已接收任务”和“暂停后继续原任务”的完整语义与可见入口，包括未开始、正在运行及已发送模型调用的边界。用户已经明确这两类需求，但目前没有可量化的使用频率，不能用任务数量推算其优先级。

## 解释边界

至少 3 条文字任务能用[章节修复](chapter-selection-fix.md)、[费用恢复](cost-accounting-recovery.md)及[费用异常验收](cost-admission-incident-20260921.md)中的明确操作编号识别为上线验收；其他验收记录无法全量自动排除。`clear` 也可能是验收或正常换对话，不能当作停止意图。同键重传只保留一个业务操作，观察 GET 不新增操作，所以当前执行库无法准确计数刷新、重连或重复点击。终结记录受留存期限制，历史样本并非完整长期总体。

## 第 2 步需要回答的问题

1. 用户点“停止”时，未开始的派发、正在执行的阶段和已发送的模型调用分别如何处理；如何清楚告知后者可能仍会结算。
2. 停止应保留当前对话及已完成结果，还是结束整页；A2 单题、A3 多题、首次题目状态尚未保存时分别允许什么。
3. 暂停请求何时才能成为真正的 `PAUSED`，恢复是否沿用原业务操作与收据，以及授权、额度和排队期限如何重新核对。若用户改变章节，应明确从哪一步重新计算、哪些已发调用和已保存结果仍归属原任务；不能把改参伪装为原输入的简单恢复。

完成上述契约后，再判断第 7 阶段的最小暂停/继续实现范围。题库保留测试等不相关遗留问题不并入此阶段。
