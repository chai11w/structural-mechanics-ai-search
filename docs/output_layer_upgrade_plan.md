# 题库 Agent 输出层升级：方向方案

## 一句话结论

题库 Agent 的下一项产品可靠性升级，不是先加“会闲聊的总控大脑”，而是补一个统一的**用户输出层**：让内部流程继续严格、分层地工作；让用户只看到清楚、安全、可行动的结果。

这层要保护已有固定话术，而不是推倒重来。

## 当前问题

现在 Agent 的内部流程已经比较复杂：A2 单题检索、A3 整页拆题、状态机、图片分流、裁图、章节判断、候选与答案，都各自有明确职责。

这带来一个自然问题：内部需要保留很多技术状态、失败原因和处理细节，但用户不应该看到它们。用户真正需要的是：

- 这次有没有成功；
- 如果没成功，是什么“用户能理解的原因”；
- 我现在该做什么；
- 这一步是否还可以继续、重试、换题或重新上传。

目前已经有不少固定、正确的用户回复，但输出逻辑散布在各个流程中。风险不一定是每条文案都不好，而是新增流程或异常分支时，容易出现以下情况：

- 内部错误码、异常名称或技术描述露给用户；
- 同类失败在 A2、A3、网页和流式接口中说法不一致；
- 用户只看到“失败”，却不知道下一步能做什么；
- 为了让回复自然，未来有人可能直接把内部原始信息交给模型润色，带来误导或信息泄露风险。

## 真正目标

目标不是“让 Agent 更会说话”，而是建立一条稳定原则：

> 内部结果可以复杂；发给用户的回复必须简洁、可信、可执行。

具体来说，输出层要做到：

1. 成功时：按已有规则清楚告诉用户结果和下一步。
2. 等待用户操作时：明确告诉用户要选什么、怎么选，不让用户猜当前卡在哪。
3. 失败时：不暴露内部细节，解释成用户能理解的原因，并给出系统允许的下一步。
4. 不确定时：诚实说不确定，要求必要的补充或确认，不假装已经识别成功。
5. 所有渠道：同一个业务结果应有一致的用户表达。

## 核心思路：统一出口，不是统一改写

可以把输出层理解为前面说的“最后一道翻译和安全检查”。

```text
内部状态 / 工具结果 / 错误原因
            ↓
       用户输出层
            ↓
      用户看到的回复
```

它不做检索、不裁图、不决定章节、不改变状态，也不代替 A2/A3 的业务判断。它只负责把已确定的结果转成合适的话。

关键原则是：**现有固定输出优先。**

```text
已有固定且正确的文案 → 原样输出
已有明确异常规则       → 用固定友好文案输出
新异常 / 未覆盖情况    → 用安全兜底文案输出
复杂但低风险的解释     → 未来才考虑受约束地润色
```

因此，“所有输出经过输出层”不等于“每句话都交给大模型改写”。它更像机场安检：正常内容快速放行，异常内容按规则处理，不能确认时走安全兜底。

## 例子

内部出现：

```text
invalid_observation_schema
```

用户不应看到：

> 模型返回的 Schema 不符合要求。

用户应该看到的是：

> 这张整页题图暂时无法可靠地区分各小题。请圈出或裁剪你要查的那一道题，我再继续检索。

内部出现：

```text
候选为空，当前章节已检索完成
```

用户应该看到：

> 我在当前章节里没有找到足够相似的题。你可以换一个章节，或发一张更清楚的题图。

内部出现：

```text
当前阶段等待用户选择整页中的题目
```

用户应该看到：

> 这页已识别出 3 道可检索题，请回复“第 1 题”到“第 3 题”选择。

这些话的事实不是输出层自己猜的；事实、可选动作都必须由原来的状态机和业务流程提供。

## 输出层的边界

输出层可以：

- 屏蔽内部错误和技术术语；
- 统一同类情况的用户表达；
- 根据已给出的状态，提示下一步允许做什么；
- 保留并放行你已经确定的固定文案；
- 作为未来“自然语言润色”的安全边界。

输出层不能：

- 自己决定继续检索、跨章节搜索、重试或跳过确认；
- 修改候选编号、题号、章节、答案等事实；
- 把“未找到”说成“已找到”；
- 把模型原话、异常栈、路径、密钥或内部代码带给用户；
- 为了自然而替换现有关键业务话术。

## 与“输入总控大脑”的关系

我们讨论过两层能力：

| 层 | 作用 | 当前必要性 |
| --- | --- | --- |
| 输入总控大脑 | 闲聊、能力说明、粗路由到 A2/A3 | 提升体验，可后置 |
| 用户输出层 | 把所有内部结果安全、清楚地交给用户 | 产品可靠性缺口，优先补 |

输入总控解决“用户怎么和 Agent 聊得更自然”；输出层解决“Agent 无论内部发生什么，都不能把不该给用户看的内容直接抛出去”。

所以，输出层是更靠近核心产品质量的优先项。

## 推荐的推进方式

第一步不是立刻重构，而是确认现状：哪些正常文案已经很好、哪些异常出口可能泄露内部信息、哪些状态缺少下一步提示。

之后只补缺口：

- 保留已有固定话术；
- 为常见失败提供稳定、用户友好的说法；
- 给未知失败准备一个不会误导的统一兜底；
- 确保网页、接口和后续入口表达一致。

第一阶段不需要新增模型调用。等这一层稳定后，如果确实需要把复杂过程解释得更自然，再把“输出模型润色”作为可选能力接在它里面，并始终允许回退到固定文案。

## 给下一对话的任务说明

请先围绕本方案审查当前题库 Agent 的用户输出：已有固定输出哪些应保持不动，异常输出是否存在泄露内部信息或缺少下一步提示的缺口。先报告问题和最小改动建议；不要直接把所有回复改成模型生成，也不要实现输入总控大脑。确认范围后，再只补统一、安全的输出兜底能力。
