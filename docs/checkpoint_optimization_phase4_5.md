## 数据语义

- 用户原图和每版裁图使用独立 Artifact，保留现有 owner、TTL、校验和审计。
- 候选题使用题库引用，另存当时的候选 ID、分数、排名、可见性。
- 答案使用有顺序的题库引用，记录当时选择的候选和 candidate generation。不再为 Checkpoint 复制答案图片；业务交付所需的图片复制不属于本轮删除范围。
- 题库引用由题库标识、章节和规范化相对定位组成，通过服务端配置映射根目录。禁止记录会话临时答案路径、绝对路径、URL 或可越界的定位。
- 引用语义是“题库当前文件”，不是历史字节快照。答案以后修正或删除，历史引用将看到当前版本或不可用；本轮不引入历史题库版本库。
- 证据清理只能删除引用，不能删除题库文件。诊断读取必须先经过 Checkpoint 的权限、TTL 和审计检查，再通过受控题库根解析文件。
- 新引用记录采用可区分的结果版本，保留旧 Artifact 记录读取。旧读取器必须明确拒绝不支持的新记录，不能把引用误当成已复制的图片。

## 阶段输入和文件生命周期

- 在接触 Store、图片或其他可能等待的操作前，冻结本次阶段需要的数据及身份；不持有 live state、可变 ToolResult 或模型客户端作为待处理内容。
- A3 重新裁剪必须创建新文件名，不能覆盖前一版。后续阶段使用显式选中的资源版本，而不是根据 unit 推测“最新路径”。
- 文件删除导致证据不可用时明确降级，不读取另一版文件补位。后续队列需要有限资源保留或租约；4.5.2 不承诺进程崩溃后仍可执行未提交采集。
- 输入副本有字节、层数和条目上限，拒绝超限采集不能影响业务。输入不进入公共协议、Trace 或未受控日志。

## 异步与故障边界

- 4.5.3 区分 accepted/queued 和 stored。只有实际提交才可以发布 `checkpoint_id` 的 Trace 关联。
- 队列同时限制条数、字节数和任务年龄；队列满立即拒绝，禁止同步回退、每请求新建线程或无界重试。
- 固定消费者按完整 owner/revision/unit 协调最近已提交前驱和最近成功前驱。丢弃节点不能留下指向未提交 ID 的因果链。
- A3 父流程与嵌套 A2 共用同一请求的采集预算；预算只统计采集开销，不消耗正常模型等待时间，不在每个阶段重置。
- 不绕过 Store 的容量、TTL、完整性和查看审计。4.5.4 把大批清理留给有边界的维护流程，保留备份、plan/hash/漂移检测和管理确认规则。
- 健康状态区分成功、积压、超龄、丢弃、资源缺失和失败。停机排空有明确上限，不无限 join。Python 线程无法安全强杀，不能宣称线程超时取消了已经运行的 I/O。

## 4.5.3 异步采集

`AsyncCheckpointRecorder` 是启用采集时启动器统一注入 A2/A3 的入口。应用 lifespan 启动一个固定消费者；请求侧只验证、冻结必要输入并尝试入队。前驱查询及其审计、图片摘要/解码、A3 Prompt 读取、Artifact/Checkpoint 写入和 Trace 关联均由消费者执行。同步 Recorder 保留为底层执行器和旧契约测试入口，生产启动器不提供同步回退选项。

| 限制 | 默认值与含义 |
| --- | --- |
| 数量 | 128，包含正在处理的 1 项，阻塞期间仍计入容量 |
| 字节 | 8 MiB，按冻结输入、完整 context 编码和每项固定记账余量累计；不是进程 RSS 承诺 |
| 年龄 | 120 秒，单调时钟，在出队及前驱查询后检查；过期任务不开始后续采集 |
| 请求提交预算 | 100ms，累计 A3 父阶段、并发 unit 和子 A2 的冻结/入队准备耗时；不把阶段间模型等待计入，不在每阶段重置 |
| 消费者 | 每个 Recorder 固定 1 个；没有每请求新线程、同步回退或采集重试 |

这些是显式代码默认值，可在隔离代码构造器中调整，现有生产 CLI 的采集开关与七项 Store 容量参数保持原样。后续容量校准归 4.5.5；100ms 是尽力而为的提交预算，不能取消已经执行的 CPU 或 I/O，也不等于测得的 P99。

`CAPTURE_QUEUED` 只表示已接纳，返回 `stored=False` 且没有 `checkpoint_id`。只有 Store 成功提交后的对象才能发布 Trace 关联，事件明确使用该对象的 trace/request/owner，不继承消费者线程的可变上下文。队列满、字节满、超龄、请求预算耗尽、清理竞争和关闭分别返回稳定原因；健康信息包含 queued/stored/rejected/expired/failed、pending、pending_bytes、worker_alive，公共健康投影同步 pending 和 queue_capacity。

消费者用经过 Store 权限、TTL、完整性和审计的查询，分别取得最近已提交和最近成功节点。严格按 identity/session/workflow/search/unit 及父子 revision 匹配，允许原有逻辑任务内 candidate generation 随阶段更新；每个任务保留自己的完整冻结 owner。没有本 scope 前驱时只按合法父 unit、父页回溯，失败或丢弃的写入不能生成虚构前驱。队列按接纳顺序处理并发到达的阶段，不为缺失阶段补造结果。

原图和裁图使用最长 120 秒的进程内资源租约，数量受同一队列限制。会话清理只保留已有有效租约的不可变文件，完成或丢弃后释放并删除已被清理标记的旧文件；后续创建的新文件名不受影响。清理进行时新租约直接拒绝，清理过程不持有队列锁。过期租约不阻止正常清理；文件缺失明确降级，不查找另一版本。此机制不提供进程崩溃恢复。

本次只接入必要的启动/关闭顺序：先停止接纳并尝试等待消费者 2 秒，再交还应用生命周期。正在执行的 Python I/O 不能强杀；Trace 关闭、维护等待预算、熔断、完整有限停机与运行任务超时协调仍由 4.5.4 验收，本节不宣称 F1/F2 已完成。

## 4.5.4 后台故障边界

每个采集任务共享 2 秒协作式 I/O 预算；Python Store/Trace 路径锁单次最多等 250ms，SQLite 等待取配置、剩余预算和 250ms 的最小值，长 SQL 使用 progress handler，提交前再次检查预算。已进入的操作系统文件读写无法强杀：超预算在途任务显示 `stalled`，拒绝新采集，保留唯一消费者，不补建线程或重试业务模型。

连续 3 次证据失败或证据不完整后，采集熔断 5 秒，期间排队任务明确丢弃。冷却后由新任务探测恢复，成功清除采集当前故障并增加 `recoveries`；业务自身的失败或降级已完整记录时不算存储故障。Store/Trace 既有历史故障计数仍保留，整体 health 可能继续提示历史问题，不能把采集恢复计数当作全部证据已补齐。

采集与维护通过独立 `.checkpoint_capture.lock` 文件互斥，竞争立即拒绝。维护继续持有原 Trace 维护锁，保留备份、plan/hash、漂移及权限边界。采集预算内容量不足不触发同步大批 purge。周期维护使用每个应用生命周期唯一的 daemon，运行预算 30 秒，SQLite 备份分批检查取消；卡住时没有后继并发维护，健康显示在途/超时状态。

关闭采集默认等待 2 秒，期限结束后移除仍在队列中的任务，增加 `shutdown_dropped`；卡住的 1 项仍计入 `pending/running`，返回后协作取消会阻止后续证据提交。Trace 写入预算 500ms，`flush` 默认最多等 5 秒，`close` 默认最多等 2 秒；超期丢弃排队事件，仍执行的 I/O 和关闭回调由固定 daemon 收尾。Trace health 只读内存，容量是最近后台写入时采样值，启动后尚未采样不代表容量为零。维护停机只等 200ms，不占用 asyncio 默认线程池等待无法终止的维护 I/O。

默认完整证据停机等待约 4.2 秒（维护 0.2、采集 2、Trace 2），不承诺线程已被系统终止，也不包括正常业务请求自身的排空。公开 health 提供 pending、running、backlog、pending_bytes、stalled、circuit_open 和维护在途状态；排队、存储、失败、超龄、熔断丢弃、关闭丢弃、资源不可用及恢复分别计数。没有添加生产开关或修改既有启动参数。
