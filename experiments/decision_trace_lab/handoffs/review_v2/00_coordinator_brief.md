# 评审模块 V2 协调说明

## 目标

把现有“逐事件阅读 JSON 并逐项打标签”的评审体验，改造成结果优先的诊断流程：

1. 先展示用户输入、Agent 最终回答和必要上下文，让评审者判断最终结果；
2. 最终结果正确时允许一键结束，不强迫逐事件复核；
3. 最终结果错误、部分正确或无法判断时，展示本回合实际决策因果链；
4. 评审者按需选择一个或多个怀疑问题点，不预设固定数量；
5. 评审者可以填写错误原因，但不强迫填写正确答案；
6. 原始 JSON 保留为折叠技术详情；
7. 自动一致性检查应主动突出可疑节点；
8. 未选择的中间事件保持未复核，不能自动算正确；
9. 观测和标注失败不得改变真实 Agent 的业务行为或结果。

## 用户已确认的工作方式

- 通常先判断最终回答，再反推问题位置；
- 不愿被迫补写正确结果，但愿意写错误原因；
- 关键项不是固定数量，重点是能发现真正出现问题的节点。

## 三角色文件交接协议

- 产品 Agent：只负责方向、范围、优先级和验收标准，写 `10_product_spec.md`；不得改业务代码。
- 执行 Agent：必须先读本文件和产品文件，实施后写 `20_execution_report.md`，包含改动文件、测试和证据。
- 审查 Agent：必须读产品与执行文件，写 `30_review_report.md`，分别给出产品结论和执行结论；不通过时明确退回哪个角色。
- 返工文件依次使用 `11_product_revision_N.md`、`21_execution_revision_N.md`、`31_review_revision_N.md`。
- 每轮返工必须包含新的问题、新的改动或新的验证证据，禁止重复同一结论。
- 任一角色上下文不足时，先在本目录写角色交接文件，再由主 Agent 更换同角色 Agent。

## 主 Agent 的循环控制

- 一次只允许责任角色处理审查明确指出的问题；
- 同一问题连续两轮没有新增证据时，主 Agent 终止该路径并重新拆解问题；
- 只有产品方向和执行结果都通过，且主 Agent 完成独立验证后才能交付。
